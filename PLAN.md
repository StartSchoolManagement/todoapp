## 1. Architecture

```
Browser ──► Next.js (App Router)
              ├─ Server Components  ── read todos via Supabase server client (cookies)
              ├─ Server Actions     ── create / toggle / update / delete
              ├─ proxy.ts           ── refresh Supabase session cookie on every request
              └─ Client Components  ── forms, optimistic UI, shadcn primitives
                      │
                      ▼
            Supabase (Postgres + Auth)
              └─ todos table, RLS: auth.uid() = user_id
```

- **Reads** happen in Server Components. No client-side fetching for the list.
- **Writes** go through Server Actions that call `revalidatePath('/')`. Client uses `useOptimistic` so toggling feels instant.
- **Auth state** lives in HTTP-only cookies managed by `@supabase/ssr`. Note: Next.js 16 renamed `middleware.ts` to `proxy.ts`; follow the current Supabase SSR docs, not older tutorials.
- **Security boundary is RLS**, not app code. Even if a Server Action has a bug, a user cannot touch another user's rows.

## 2. Data model

```sql
create table public.todos (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id) on delete cascade,
  title       text not null check (char_length(title) between 1 and 200),
  notes       text,
  is_done     boolean not null default false,
  due_date    date,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

create index todos_user_id_created_at_idx on public.todos (user_id, created_at desc);

alter table public.todos enable row level security;

create policy "owner can read"   on public.todos for select using (auth.uid() = user_id);
create policy "owner can insert" on public.todos for insert with check (auth.uid() = user_id);
create policy "owner can update" on public.todos for update using (auth.uid() = user_id);
create policy "owner can delete" on public.todos for delete using (auth.uid() = user_id);

-- updated_at trigger
create or replace function public.set_updated_at() returns trigger as $$
begin new.updated_at = now(); return new; end; $$ language plpgsql;

create trigger todos_set_updated_at before update on public.todos
  for each row execute function public.set_updated_at();
```

Everything is user-scoped. No `profiles` table in v1; `auth.users` is enough.

### Phase 3 — Auth
**Goal:** sign up, log in, log out, protected routes.

1. `src/lib/supabase/client.ts` — `createBrowserClient`.
2. `src/lib/supabase/server.ts` — `createServerClient` with the cookie `getAll`/`setAll` adapter, using `await cookies()`.
3. `src/lib/supabase/proxy.ts` + `src/proxy.ts` — refresh session, redirect unauthenticated users hitting `(app)` routes to `/login`, and authenticated users hitting `/login` to `/`.
4. `(auth)/login` and `(auth)/signup` pages with shadcn `Card` + `Input` + `Button`. Server Actions `signIn`, `signUp`, `signOut` in `src/lib/auth/actions.ts`. Validate input with zod. Surface errors via `useActionState`.
5. `auth/callback/route.ts` to exchange the code when email confirmation is on.
6. `(app)/layout.tsx` calls `supabase.auth.getUser()` server-side; redirects if null; renders header with user email + sign-out button.

**Checkpoint:** Fresh browser → `/` redirects to `/login`. Sign up → lands on `/`. Refresh keeps you in. Sign out → back to `/login`. Two different accounts in two browsers see independent sessions.

### Phase 4 — Core todo CRUD
**Goal:** the actual app. Add, list, toggle, edit, delete.

1. `src/lib/todos/schema.ts` — zod: `createTodoSchema`, `updateTodoSchema`.
2. `src/lib/todos/queries.ts` — `getTodos()` ordered by `is_done asc, created_at desc`.
3. `src/lib/todos/actions.ts` — `createTodo`, `toggleTodo`, `updateTodo`, `deleteTodo`. Each: parse with zod → get user → write → `revalidatePath('/')`. Return `{ error?: string }`, never throw to the client.
4. `(app)/page.tsx` — Server Component: fetch todos, render `<AddTodoForm />` + `<TodoList initialTodos={todos} />`.
5. `todo-list.tsx` — client; `useOptimistic` for toggle and delete so the UI never waits on the round-trip.
6. `todo-item.tsx` — checkbox, title (strikethrough when done), due date badge, dropdown menu with Edit / Delete. Edit opens a `Dialog` with title/notes/due date.
7. `empty-state.tsx` when the list is empty.
8. Toast errors via `sonner` when an action returns `error`.

**Checkpoint:** Full CRUD works. Reload after each action shows persisted state. Opening the app as user B shows none of user A's todos. Network tab shows no client-side fetch of the list.

## 5. Risks & gotchas

| Risk | Mitigation |
|---|---|
| Next.js 16 `proxy.ts` vs older `middleware.ts` tutorials | Follow the official Supabase "Server-Side Auth for Next.js" docs for the current version; ignore blog posts older than 2026. |
| `cookies()` is async in Next 15+/16 | Always `await cookies()` in `server.ts`. |
| Forgetting RLS → data leak | Phase 2 checkpoint explicitly tests it before any UI exists. |
| Email confirmation loop in dev | Disabled in Phase 2, re-enabled in Phase 6 with a checklist item. |
| shadcn `ui/` files drifting | Never hand-edit; re-run `npx shadcn@latest add <name> --overwrite` if needed. |
| Optimistic UI diverging from server | Actions always `revalidatePath`; optimistic state is discarded on the next server render. |
